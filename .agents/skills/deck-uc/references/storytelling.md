# Storytelling para presentaciones UC

Guía metodológica para construir la historia **antes** de diseñar las diapositivas. No contiene ejemplos, nombres ni referencias corporativas del taller fuente.

## Principio rector

Una presentación efectiva combina **datos + narrativa + soporte visual**. Los datos deben transformarse en un insight, el insight debe conducir a una decisión o acción, y la historia debe poder comprenderse sin depender de conocimiento implícito del autor.

## 1. Definir audiencia antes de escribir

Clasificar la audiencia por su relación con el tema y la decisión:

- **Liderazgo ejecutivo:** poco tiempo; necesita conclusión, implicancia y decisión rápidamente.
- **Equipo técnico:** conoce el tema; requiere precisión, supuestos, método y evidencia.
- **Audiencia mixta:** necesita lenguaje común y capas de detalle.
- **Equipo amplio:** priorizar contexto, claridad, relevancia y recordación.

Antes de construir la historia responder:
1. ¿Qué le importa a esta audiencia?
2. ¿Qué nivel de conocimiento tiene?
3. ¿Qué debe hacer después de escuchar?
4. ¿Cuál es su principal dolor o tensión respecto del tema?
5. ¿Ya tiene una opinión formada?

**Regla:** la audiencia define el tono, el nivel de detalle, la secuencia y el tipo de evidencia.

## 2. Definir el objetivo de comunicación

No comenzar por las diapositivas. Primero establecer qué cambio debe producir la presentación.

Objetivos típicos:
- **Informar:** compartir estado, avance, hallazgo o resultado.
- **Alinear:** validar criterios, coordinar o tomar una decisión conjunta.
- **Explorar:** diagnosticar, idear o co-construir.
- **Activar:** inspirar, lanzar o movilizar hacia una acción.
- **Priorizar / decidir:** elegir entre alternativas, aprobar, rechazar o cambiar el rumbo.
- **Escalar:** resolver un bloqueo urgente.

Escribir una frase: **“Al terminar, quiero que la audiencia recuerde / entienda / decida / haga ______.”**

## 3. Definir la Big Idea

Toda la presentación debe apuntar a **un insight principal**. La Big Idea es aquello que la audiencia debería recordar aunque olvide el resto.

Criterios:
- una sola idea central;
- expresable en 1–2 frases;
- clara y simple, sin jerga innecesaria;
- relevante para la audiencia;
- respaldable con evidencia disponible;
- conectada con el objetivo de comunicación.

Si la Big Idea no puede explicarse en aproximadamente tres minutos junto con sus argumentos esenciales, simplificar antes de diseñar.

## 4. Elegir arquitectura: deductiva o inductiva

### Deductiva — conclusión primero

Usar cuando la audiencia necesita llegar rápido a la decisión, especialmente en contextos ejecutivos.

Secuencia:
1. Recomendación / conclusión.
2. Resumen de argumentos.
3. Argumentos principales.
4. Evidencia que respalda cada argumento.
5. Próximo paso o decisión requerida.

### Inductiva — evidencia primero

Usar cuando la audiencia necesita construir confianza en la conclusión, está poco informada, es escéptica o requiere comprender el razonamiento.

Secuencia:
1. Evidencia / hechos relevantes.
2. Hallazgos.
3. Implicancias.
4. Conclusión lógica.
5. Recomendación o acción.

**No elegir por gusto visual:** elegir según audiencia, contexto y objetivo.

## 5. Construir el arco SCR

Usar **Situación – Conflicto – Resolución** como estructura base cuando exista un cambio, tensión o problema que explicar.

- **Situación:** realidad o estado actual necesario para entender el tema.
- **Conflicto:** qué cambió, qué tensión apareció, qué impide seguir igual o por qué importa ahora.
- **Resolución:** nueva realidad, conclusión, recomendación o acción que responde al conflicto.

Prueba de calidad: si se elimina el conflicto y la historia sigue funcionando igual, probablemente falta tensión narrativa o relevancia.

## 6. Escribir la lógica con Dot–Dash

Construir la historia en texto plano antes de abrir el diseño.

- **Dot:** afirmación principal de una sección. Debe poder convertirse directamente en el **action title** de una diapositiva.
- **Dash:** evidencia, argumento o dato que demuestra el Dot.

Ejemplo abstracto:

- **Dot:** [afirmación que la audiencia debe entender]
  - Dash: [evidencia 1]
  - Dash: [evidencia 2]
  - Dash: [implicancia]

Cada Dot debe responder: **¿qué quiero que concluya la audiencia de esta lámina?**

## 7. Convertir la historia en títulos de acción

Los títulos no deben limitarse a nombrar el tema (“Resultados”, “Contexto”, “Análisis”). Deben comunicar la conclusión de la lámina.

Reglas:
- escribir una afirmación completa;
- priorizar lenguaje comprensible para una persona no especialista;
- evitar siglas o tecnicismos si no son imprescindibles;
- hacer que la secuencia de títulos pueda leerse como un resumen ejecutivo;
- una lámina = una idea principal.

**Prueba del storyboard:** leer solo los títulos, en orden. Si no cuentan una historia coherente, reescribir antes de poblar las láminas.

## 8. Storyboard antes del diseño final

Pasar los Dots a una vista de storyboard (miniaturas, tarjetas, post-its o una hoja dividida). Para cada lámina definir únicamente:

1. action title;
2. evidencia indispensable;
3. visual más adecuado;
4. transición lógica con la siguiente lámina.

No diseñar en detalle hasta validar la secuencia completa.

## 9. Simplificar sin excluir

La simplificación no significa quitar rigor. Significa reducir la carga cognitiva sin ocultar información necesaria.

Buenas prácticas:
- comenzar por el mensaje, no por el dato;
- eliminar información que no cambie la conclusión;
- mover detalle técnico a anexos cuando la audiencia principal no lo necesita;
- usar lenguaje claro y directo;
- definir siglas en el primer uso;
- preferir ejemplos, comparaciones o visualizaciones cuando faciliten comprensión;
- separar “lo que sabemos” de “lo que inferimos”;
- no asumir que algo es obvio solo porque lo es para quien hizo el análisis.

## 10. Datos y soporte visual

Cuando exista data compleja, usar gráficos, diagramas o visualizaciones para hacer visible el patrón que sostiene el mensaje.

Reglas:
- el gráfico debe responder al action title;
- destacar solo el dato que sostiene la conclusión;
- evitar elementos decorativos que compitan con el mensaje;
- no usar una tabla cuando la tarea sea comparar tendencias visualmente;
- no usar un gráfico cuando uno o dos números grandes comuniquen mejor;
- mantener trazabilidad de cifras y fuentes;
- nunca inventar datos para completar una narrativa.

## 11. Flujo obligatorio para deckUC

Antes de generar el plan JSON:

1. Leer las fuentes del usuario.
2. Definir audiencia.
3. Definir objetivo de comunicación.
4. Redactar Big Idea.
5. Elegir estructura deductiva o inductiva.
6. Construir SCR cuando corresponda.
7. Escribir Dot–Dash en texto plano.
8. Convertir Dots en action titles.
9. Crear storyboard y validar continuidad leyendo solo los títulos.
10. Recién entonces elegir layouts UC y poblar evidencia.
11. Ejecutar QA visual y QA narrativo.

## 12. QA narrativo obligatorio

Antes de entregar, comprobar:

- [ ] La audiencia y el objetivo están explícitamente definidos en el plan de trabajo.
- [ ] Existe una Big Idea única.
- [ ] La secuencia elegida (deductiva/inductiva) es coherente con la audiencia.
- [ ] El conflicto o la relevancia del tema aparece temprano.
- [ ] Cada lámina tiene una sola idea principal.
- [ ] Cada título expresa una conclusión, no solo un tema.
- [ ] Los títulos, leídos solos, cuentan una historia completa y coherente.
- [ ] Cada afirmación importante tiene evidencia trazable.
- [ ] El nivel técnico corresponde a la audiencia.
- [ ] La presentación termina con una conclusión, decisión o próximo paso claro cuando el objetivo lo requiere.
- [ ] No hay información decorativa o redundante que distraiga de la Big Idea.
